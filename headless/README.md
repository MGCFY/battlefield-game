# 战场沙盘 · 无头高速模拟环境

把 `battlefield-v3.9.15.html` 这个单文件游戏，变成可在 Node 里**无浏览器、无渲染、可并行、可复现**地跑完整对局的模拟器，并把规则 AI 的对局直接转成**神经网络可训练的行为克隆数据集**。

一句话价值：**同一份规则代码，既能给玩家玩，也能给 AI 训练用**——不存在"训练环境和实际游戏规则不一致"的漂移。

> **源文件解析顺序**（可用 `--src` 覆盖）：`battlefield-game/battlefield-v3.9.15.html` →
> `battlefield-v3.9.14.html` → `桌面/battlefield-v3.9.13(1).html` → 仓库内其它同名版本。
> 当前基线是 `battlefield-v3.9.15.html`（= `battlefield-v3.9.13(1).html` + 4 处修复，见第七节）；
> 旧版 `battlefield-v3.9.13(1).html` / `battlefield-v3.9.14.html` 保留在仓库里作为 A/B 对照。

---

## 一、为什么是"单一真源"而不是"抽一个 core.js"

训练方案里把「抽出 `core.js`」列为唯一高风险项，因为把规则从 HTML 里**复制/重写**一遍，
任何一处细节差（某个 ±1、某个取整、某处随机顺序）都会让训练出来的策略在真实游戏里失效。

本环境换了个思路：**不抽取，直接加载**。

```
engine.js  →  读取 .html → 正则取出 <script> 原文 → 注入导出层 → vm 沙盒执行
```

- 规则代码**按原样加载、不改写一个字节**（`selfcheck.js` 第 [1] 关逐字节验证：v3.9.15 为 251,474 字节全等；
  v3.9.14 为 251,336；v3.9.13 基线为 250,594）
- 唯一改动：裁掉文件末尾的 `renderLegend(); showWelcome();` 自动启动调用（86 字节）
- 游戏升级到 v3.9.15 时，**把新 HTML 换进来即可**，环境自动跟进

规避了 M1 的全部风险，代价是必须把浏览器侧的东西全部打桩（DOM / 定时器 / storage / canvas），
这部分已经做完，见 `buildSandbox()`。

## 二、文件

### 对局模拟

| 文件 | 职责 |
| --- | --- |
| `engine.js` | **核心**。加载 HTML、DOM/BOM 打桩、注入可复现 RNG、导出内部状态与函数、对渲染类函数打 no-op 补丁 |
| `policies.js` | 策略库：`ai:easy/medium/hard`、`rush`、`turtle`、`hold`、`random`，并支持自定义策略对象 |
| `sim.js` | 对局驱动 + 统计：部署、交替行动、胜负与回合数、批量汇总、目标校验 |
| `env.js` | **RL 契约**：`reset / step / observe / encode / masks / actionSpace`，因子化动作 + 动作掩码 |
| `cli.js` | 命令行入口（批量统计、目标校验、JSON 导出、并行调度） |
| `worker.js` | **常驻并行执行器**（`worker_threads`，pull 调度） |
| `proc-worker.js` | 进程级并行执行器（NDJSON 协议，`--mode process`） |
| `selfcheck.js` | 模拟器五关一致性自检 |
| `bench.js` | 性能基准 |

### 行为克隆数据采集

| 文件 | 职责 |
| --- | --- |
| `collect.js` | **核心**。给游戏动作原语打钩子，抓取教师的 (观测, 掩码, 实际动作)；流式写分片并合并为 `.npy` |
| `collect-worker.js` | 采集的并行分片执行器 |
| `npy.js` | 极简 `.npy` 读写（`np.load` 直接可用，训练侧零解析代码） |
| `load_bc.py` | **Python 侧加载器**：`load_bc()` / `dense_masks()`，直接产出 numpy / torch 张量 |
| `selfcheck-collect.js` | 采集七关自检（含「钩子零扰动」等价性证明） |

### 验收与诊断

| 文件 | 职责 |
| --- | --- |
| `accept.js` | **AI 验收门禁**：一条命令跑完七项（中等档六项 + 简单档防回归一项），不达标退出码 1，可接 CI |
| `diag-turtle-endgame.js` | 龟缩对局**终局画像**：把超时局按终局兵力形态自动归类，直接指出「为什么打不完」 |
| `probe-turtle.js` | 单局逐步探针：逐回合打印 doctrine / 破龟缩阶段 / 双方兵力 / 距敌基地距离 / 在射程圈内的单位数 |
| `probe-branch.js` | **分支指纹探针**：包装动作原语，逐单位记录本回合走了哪条决策分支（含「空转」） |

> 后三个是这次定位「打不完」时现造的工具，实战价值很高：`diag-turtle-endgame` 一跑就知道该往哪查，
> `probe-branch` 一跑就知道某个单位是「不想动」还是「动不了」。

## 三、快速开始

```bash
cd battlefield-game/headless

# 列出可用策略
node cli.js --list

# 看一局的完整过程（胜负 + 回合数 + 态势曲线）
node cli.js --trace --red rush --blue ai:medium

# 批量跑 400 局，自动校验「中等AI 对 速推流 ≥80%」（视野缓存默认开启）
node cli.js -n 400 --red rush --blue ai:medium

# 龟缩流专项（校验 ≥60% 且平均 <100 回合）
node cli.js -n 200 --red turtle --blue ai:medium --max-rounds 200

# 导出逐局明细 / 性能基准 / 一致性自检
node cli.js -n 500 --red rush --blue ai:medium --json out.json --detail
node bench.js 30 ai:medium rush --cache
node selfcheck.js 12
```

命令行会自动根据双方策略推断校验目标；也可以用 `--assert blue:0.8` 或
`--assert blue:0.6:100` 指定。**校验不通过时进程返回码为 1**，可直接接 CI。

### 一键验收（AI 难度调优用这条）

```bash
# 跑完七项（中等档六项 + 简单档防回归一项）
node accept.js --src ../battlefield-v3.9.15.html

# 小样本冒烟 / 放大样本
node accept.js --quick
node accept.js --scale 2

# 指定源文件对比（不传则用 DEFAULT_SRC 里的最新版）
node accept.js --src "../battlefield-v3.9.13(1).html"
```

### 定位「为什么打不完」

```bash
# 1) 终局画像：把超时局自动归类，指出该往哪查
node diag-turtle-endgame.js -n 40 --src ../battlefield-v3.9.15.html

# 2) 逐步探针：看某一局的态势曲线
node probe-turtle.js --seed 1 --max-rounds 200 --every 4 --src ../battlefield-v3.9.15.html

# 3) 分支指纹：看某个单位本回合到底走了哪条分支（含"空转"）
node probe-branch.js --seed 1000 --from 190 --to 198 --side 0 --src ../battlefield-v3.9.15.html
```

### 采集行为克隆数据

```bash
# 采集 120 局「困难 AI vs 中等 AI」的教师决策（约 10 万条样本）
node collect.js -n 120 --red ai:hard --blue ai:medium --out data/bc_hard

# 只要动作与掩码，不要观测图（体积极小，用于统计覆盖度）
node collect.js -n 500 --red ai:hard --blue rush --out data/bc_rush --obs none

# 校验采集是否可信（钩子零扰动 / 布局 / 掩码 / 确定性）
node selfcheck-collect.js 8
```

## 四、四种用法

### 1) 批量统计（最常用）

```js
const { loadEngine } = require('./engine');
const { runBatch, summarize } = require('./sim');

const env = { api: loadEngine({ visionCache: true }) };
const results = runBatch(env, { red: 'rush', blue: 'ai:medium', map: 'gen', budget: 3000 }, 200);
console.log(summarize(results).winRate);
```

### 2) 单局可复现对局

同一个 `seed` 必然得到同一局（`selfcheck` 第 [2] 关验证）。
第 i 局的种子 = `--seed + i`，因此一批实验可以完整复现。

```js
const { runMatch } = require('./sim');
const r = runMatch(api, { red: 'ai:hard', blue: 'turtle', seed: 42, map: 'scorch' });
// r.winner / r.turns / r.reason / r.survivors / r.deploySpent / r.ms
```

### 3) RL 环境（对应训练方案的「因子化动作头」）

```js
const { createEnv } = require('./env');
const env = createEnv({ side: 0, opponent: 'ai:medium', budget: 3000, visionCache: true });

let obs = env.reset({ seed: 1 });
while (!env.done) {
  const la = env.legalActions(0);              // 掩码：该单位可做哪些动作、可打哪些格
  const type = la.types[0];
  const target = la.targets[type][0];
  const { obs, reward, done, info } = env.step({ unit: 0, type, target });
}
```

**动作空间**（因子化，替代 16 万的扁平空间）：

| 头 | 维度 | 含义 |
| --- | --- | --- |
| `unit` | 64 | 己方待行动单位的索引 |
| `type` | 4 | `0` 机动/近战 · `1` 远程打击/轰炸 · `2` 休整 · `3` 待命 |
| `target` | N² | 目标格 `r*N+c`（400 @20×20，1600 @40×40） |

> **动作空间已与游戏 UI 对齐**（v2 修正）：打击目标改为「射程内全图可选」（与游戏 `strikeCells(cp)` 一致，
> 视野只影响观测、不影响开火合法性），并按高地修正逐格计算射程 `strikeRangeTo`；
> 轰炸机（`bombRange` 曼哈顿菱形）也纳入了 `type=1`。此前版本把打击目标限制在视野内，
> 导致这类决策无法采样——修正后教师决策的合法率从 97.0% 提升到 **99.86%**。

**掩码**：`masks()` 返回 `{unit, type, targets}`；`legalActions(i)` 返回单个单位的
`{types, targets}`。合法性由掩码**前置保证**——`selfcheck` 第 [5] 关用随机采样验证
「掩码内动作 100% 可执行、非法动作 0 个」。

**观测**：`observe(side)` 给结构化对象（含战争迷雾：只有进视野的敌军才有坐标）；
`encode(side)` 给 `Float32Array[N*N*12]` 特征图，可直接喂 CNN。

| 通道 | 含义 |
| --- | --- |
| 0–7 | 地形 one-hot：平原 / 高地 / 河流 / 禁区 / 城市 / 丛林 / 沙漠 / 雪地 |
| 8 | 桥面 |
| 9 | 地雷 |
| 10 | 未探明（迷雾） |
| 11 | 单位分布：己方 `+`、敌方 `−`，按兵力当量 /100 缩放；视野外敌方不写 |

### 4) 行为克隆数据采集（对应「两段式训练」的第一段）

**设计**：不重写教师策略，而是在沙盒里给 8 个「动作原语」打钩子——
`executeMove` / `performStrike` / `performKatyusha` / `performBomb` / `doRest` /
`performGroupCharge` / `resolveBattle` / `aiActOne`。
游戏内置 AI 照常决策与执行，我们在它**动手之前**把
「当时的观测 + 当时的合法动作掩码 + 它的实际选择」抓下来。

为什么这样最稳：

1. **教师就是真教师**——没有"把 AI 重写一遍"带来的行为漂移；
2. **掩码唯一真源**——采集层与 `env.js` 共用 `legalActionsFor()`，
   训练时喂给网络的掩码 == 教师决策时看到的合法集；
3. **观测在动作之前编码**——是教师真正看到的那一帧；
4. **钩子只读**——不写状态、不消耗随机数（`selfcheck-collect.js` 第 [1] 关逐字段证明：
   装钩子与不装钩子的 8 局对局，胜负 / 回合 / 残存完全一致）。

**教师动作 → 动作空间的映射**：

| 教师原语 | 映射 | 说明 |
| --- | --- | --- |
| `executeMove(p, path)` | `type=0`，target = 终点格 | 含"移动到敌格触发近战" |
| `aiStepToward` | 同上（内部走 `executeMove`） | 由钩子自动覆盖 |
| `performStrike/Katyusha/Bomb` | `type=1`，target = 打击格 | 轰炸机同路径 |
| `doRest` / AI 直接置 `resting` | `type=2`（`aiActOne` 括号内判定） | 只在掩码允许时标注 |
| `performGroupCharge(side,r,c,ids)` | 逐单位 `type=0` → 该格 | 集团冲锋按单位拆开 |
| `resolveBattle(units,r,c)` | 逐单位 `type=0` → 本格 | 原地近战 = "移动到本格攻击" |
| 未触发任何原语 | `type=3`（待命） | 兜底 |
| 投掷照明弹 / 烟幕 | **跳过并计数**（`未覆盖动作`） | 不在 4 类动作空间内，宁可不采也不错误标注 |

**输出文件**（目录由 `--out` 指定）：

| 文件 | 形状 | 说明 |
| --- | --- | --- |
| `obs.npy` | `[D, 12, N, N]` `u1`/`f4` | 观测（默认 uint8 量化，通道 0–10 无损） |
| `meta.npy` | `[D, 9]` `i4` | `game, round, turn, side, unitIdx, unitType, type, target, valid` |
| `legal_types.npy` | `[D, 4]` `u1` | 各动作类型的合法位 |
| `legal_count.npy` | `[D]` `i4` | 该决策的合法 `(type,target)` 项数 |
| `legal_items.npy` | `[K, 2]` `i4` | 合法项流 `(type, target)` |
| `legal_ptr.npy` | `[D+1]` `i4` | CSR 行指针（由 count 推出） |
| `meta.json` | — | 配置 / 特征规格 / 通道语义 / 逐局记录 / 统计 |

量化说明：通道 0–10 为 `value*255`（二值无损）；通道 11 为 `(value+1)*127`，
解码 `value = u/127 - 1`，**0 精确还原**，范围夹在 `[-1, 1]`。

## 五、性能实测

测试机：Intel i7-14650HX（8 P 核 + 8 E 核，24 逻辑核）/ 16GB / Windows / Node 22。
场景：20×20 程序生成图、3000 分预算、`ai:medium` vs `rush`（平均 27.5 回合/局）。

### 线程缩放

| 线程数 | 1 | 4 | 8 | 12 | **16（默认）** | 20 | 24 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 局/秒 | 9.3 | 33.8 | 55.1 | 62.1 | **67.7** | 50.6 | 47.9 |

- 默认并行度 = `min(核数-2, 16)`，本机即 **16**。
- 16 线程 ≈ **7.3×**（不是 16×）。这是**内存带宽 / SMT 争用**的典型曲线：
  8 线程（纯 P 核）已达 6×，再开超线程只多 22%；20/24 线程落到 E 核反而回退。
- 结论：**这台机器上完整对局吞吐的实际上限就是 ~70 局/秒**，不是 150。

### 环境交互步

| 口径 | 单核 | 16 线程（×7.3） |
| --- | --- | --- |
| 完整对局 | 9.3 局/秒 | **67.7 局/秒** |
| 环境交互步（含掩码 + 观测） | 615 step/秒 | **约 4,500 step/秒** |
| 1 亿步交互 | 45 h | **约 6.2 h** |
| 3 亿步交互 | 136 h | **约 18.6 h** |

> 方案里「≥1000 局/秒」：按**完整对局**口径差一个数量级；按**环境交互步**口径已远超。
> 1000 局/秒意味着单局要在 1ms 内跑完约 150 次带 BFS 的决策——JS 侧不现实。
> 好消息是方案自己的资源预估（1–3 亿步 → 6–18 小时）**实测吻合**（6.2–18.6 h）。

### 动态调度（pull 模式）的价值

长尾场景（`turtle` vs `ai:medium`，192 局，16 线程，回合上限 200）：

| 调度方式 | 局/秒 | 说明 |
| --- | --- | --- |
| `--chunk 1`（pull，逐局领取） | **17.4** | 线程空闲即刻领下一局 |
| `--chunk 12`（准静态分片） | 13.0 | 先跑完的线程空转 |

**+34%**。龟缩流单局耗时从 30 回合到 200 回合不等，固定切蛋糕必然浪费——这就是改成
常驻 worker + 任务队列的原因（`worker.js` + `cli.js:runPool`）。

### 提速是怎么来的

| 措施 | 收益 | 代价 |
| --- | --- | --- |
| 渲染/快照/落盘/暴露统计 13 个函数打 no-op | 约 2× | 无（`selfcheck` [3] 证明规则不变） |
| 环境侧视野缓存 + 合法动作按代际合并 | step +45% | 无（动作结算即失效） |
| 游戏内 `computeVision` 同回合记忆化（默认开启） | **3.2×** | 无（`selfcheck` [4] 验证逐局结果一致） |
| 常驻 worker 池 + pull 调度 | 长尾 +34% | 无 |
| `worker_threads`（优于独立进程 8%） | ≈ 核数倍（实测 7.3×） | 无 |

试过但**没用**的：`--mode process`（独立堆，本机比线程慢 8%）、
`--max-semi-space-size=32/64`（更大新生代 → 反而慢 25%，缓存局部性变差）、
`log()` 打 no-op（只快 3%，日志不是瓶颈）。

### 提速路线（按性价比排序）

1. **缩短对局**：`--max-rounds 100` 直接砍掉长尾（`turtle` 场景有一半的局卡在超时）。
2. **降低预算**：`--budget 1500` 让单位数减半，决策与 BFS 成本同步下降。
3. **多机集群**：单机已到内存带宽上限，横向扩展是唯一线性路径。
4. **C++ 重写**：把 `computeMoveTargets`/`computeVision`/战斗结算移植成 N-API 插件，
   预计再快 10–30×，是唯一能摸到 1000 局/秒的路线。项目里已有 `battlefield-v2.cpp` 可作起点。

| [2] 样本数一致 | 写出条数 == `.npy` 第 0 维 | ✅ |
| [2] 布局与量化 | 逐元素比对「内存编码」vs「文件字节」（含通道优先重排） | ✅ |
| [3] 掩码自洽 | 每条 `valid` 样本的动作都落在自己的掩码里 | ✅ 2805/2805 |
| [5] 通道语义 | 0–10 只取 `{0,255}`；每格恰好一个地形通道为 1 | ✅ |
| [4] 确定性 | 同种子两次采集，数据文件指纹逐一相同 | ✅ |

**关于第 [1] 关的一个已知细节**（模拟器 `selfcheck` [3] 同源）：直接对比
「跳过渲染 vs 真实渲染」的整局结果会不一致，根因不是规则被改，而是被 no-op 掉的
`beginRecord()` 里有**一次 `Math.random()`**，整条随机流因此错位一格。
所以验证时在每个阶段前重新播种，把随机流对齐后再比对，这才是「规则等价」的正确证法。
含义：**无头环境内部完全自洽可复现**，但它的随机流与浏览器里那种"边跑边渲染"的对局
不会逐帧相同——这不影响训练，只影响"用无头去复现某一场浏览器对局"。

**一句话**：`accept.js` 基线 4 项未达 → v3.9.14 六项全过 → v3.9.15 补上简单档那块短板。
（中等档六项在 v3.9.15 与 v3.9.14 **逐位相同**，因为 v3.9.15 只动简单档的编成配额。）
† v3.9.13 的 59.5% 是假象 —— 残兵不死 bug 同等保护了简单 AI 的残部，见下。

### 根因：不是 AI 不行，是规则有一个「残兵不死」bug

把 40 局超时局做终局画像，结果 **24/24 完全同构**：攻方近战全灭，只剩 1 门炮兵 + 2 架空军在射程外空转。
顺着 `probe-branch.js` 的分支指纹往下挖，抓到一条真正的规则漏洞：

```js
// strikeCellRanged() 步兵分支（同时服务炮/坦克/轰炸机）
const cap = Math.floor(before*fireCapFrac(shooter));   // heavyArt → fireCapFrac = 0.50
killed = Math.min(Math.round(acc*dmgMult), cap, before);
```

当目标只剩 **1 人**时 `Math.floor(1 × 0.5) = 0` → `killed = min(acc, 0, 1) = 0`。
**最后一兵对一切远程火力永久免疫**（炮密度再高也打不动）。实测现象：攻方 15 门重炮连续 80 回合直击同一格，
守方 1 名步兵血量纹丝不动。炮兵分支与重火力分支都写了 `Math.max(1, …)` 兜底，**步兵分支漏了**
——就是这一处不一致，制造了整个长尾：双方各自剩 1 人 → 谁也打不死谁 → 卡满 200 回合判超时。

**关键证据（三项修复的分离实验）**：

| 配置 | 龟缩胜率 | 平均回合 | 说明 |
| --- | --- | --- | --- |
| v3.9.13 基线 | 43.8% | 141.2 | — |
| 只修规则（`Math.max(1,…)`） | 53.1% | 134.7 | 残兵可杀了，但攻方炮兵还没进射程，没人去打 |
| 只修 AI（BFS 推进 + 阶段复位） | 53.1% | 129.6 | 炮兵进射程了，但残兵杀不死 |
| **两项都修** | **98.1%** | **79.0** | 缺一不可 |

顺带修掉的第二个 bug（AI 侧，用 `probe-branch` 抓到的）：

> 炮兵推进原顺序是「曼哈顿距离变小 → 贪心 `aiStepToward` → 否则 BFS」。但 `aiStepToward` 几乎必返回 true，
> 末段的 BFS 永远轮不到。遇到禁区环绕的断头路（实测敌基地 (16,16) 正上方 (3,16)~(7,16) 全是禁区），
> 重炮走到 (2,16) 后无路可下，在 **(2,15)↔(2,16) 之间来回震荡数百回合**，射程 9 的火炮整局零输出。
> 修法：一律以「到敌大本营的 BFS 步数」为进度度量 + 禁止走回上一步。

第三个 bug：`aiTurtlePhase` **只写不复位**——识别一次龟缩后整局卡在"突击/孤注一掷"分支
（实测终局 `doc=hunt` 但 `ph` 恒为 3），兵力耗尽后残部在射程外空转。

### v3.9.15：简单 AI 的编成里少了 1 架轰炸机

v3.9.14 修掉残兵不死之后，难度梯度变真实了，也顺带暴露了简单档的硬伤：
**`ai:easy` 对龟缩流掉到 42.0%**。（v3.9.13 那个 59.5% 是假象——同一个 bug 也保护了简单 AI 的残部。）

根因不在战术，在**部署配额自相矛盾**：

```js
easy: { ..., bomber:.01 }                     // frac：打算把 1% 预算给轰炸机
: {inf:q(600), ..., katyusha:0, scout:q(1,1), recon:0, bomber:0};   // 配额：却写成 0 架
```

`B=3000` 时 `frac.bomber` 只够 `round(3000×0.01/900) = 0` 架，配额又是 0 → **一架都买不到**。
于是简单 AI 顶 26~35 门重炮的炮阵时，手里没有任何空中破局手段（对照：中等档配额有 `bomber:1`）。

归因实验（`ai:easy` vs `turtle`，各 200 局，逐项单独开关）：

| 配置 | 胜率 | 平均回合 |
| --- | --- | --- |
| v3.9.14（无修补） | 42.0% | 68.2 |
| + 炮兵集群 / 前出阵地 | 44.5% | 77.5 |
| + 集团冲锋（`doCharge` 0→1） | 52.5% | 65.9 |
| + 炮兵散位 | 54.0% | 71.6 |
| + 龟缩期火力概率 0.9 | 56.0% | 70.6 |
| **只补编成：`bomber:0` → `bomber:1`** | **86.5%** | **88.9** |

**反直觉**：战术层四项全加起来只值 +14pp，而只改一个数字就是 +44pp —— 简单 AI 不是不会打龟缩，
是它压根没买破炮阵的装备。

所以 `battlefield-v3.9.15.html` **只改动 1 处逻辑 + 2 处版本号**（脚本 diff 共 3 行）：

| 编成 | v3.9.14 | v3.9.15 |
| --- | --- | --- |
| 步兵 / 骑兵 | 1860 / 80 | 1860 / 60 |
| 轻炮 / 重炮 | 28 / 12 | 12 / 11 |
| 坦克 / 侦察 | 4 / 2 | 0 / 0 |
| **轰炸机** | **0** | **1** ← 唯一改动 |

（`aiFillBudget` 自动用 1 架轰炸机 + 重炮换掉了坦克 / 侦察 / 部分轻炮，总预算 3000 不变。）

**难度梯度没被抹平**：简单 AI 对中等仍只有 40.5%，对困难 40.0%（各 200 局）。

## 九、已知限制

- **只支持单方视角的 step 接口**：`createEnv({side})` 一次控一方，对手由策略驱动。
  真正的双人自对局需要把两侧都换成外部策略（`runBatch` 里传自定义 policy 即可）。
- **采集侧假设「一单位一动作/回合」**：坦克/喀秋莎有"开火 + 移动"双动作，
  目前只记录第一个动作（后续动作不丢状态、只是不作为标签）。影响面很小。
- **投掷照明弹 / 烟幕不在动作空间内**：采集时跳过并计数（示例里 416 条）。若后续要训练
  带投掷的策略，需要把 `type` 头扩到 6 类。
- **随机流与浏览器不逐帧对齐**（见第六节）。
- **默认跳过 `updateExposure`**（战术分析字段），它不影响 AI 决策与胜负；
  需要时用 `--keep-exposure` 打开。
- **v3.9.14 的规则修复会改变所有难度档的强度**（不只中等 AI）：`ai:easy` 对龟缩流由 59.5% 降到 42.0%。
  原因是旧版"残兵不死"bug 同时保护了**简单 AI 的残部**，属虚假胜率；残部被正常清掉后，简单 AI 就暴露出
  它本来没有破龟缩手段。这不是回归，是难度梯度变真实了。
  **v3.9.15 已单独给简单档补上破局装备**（配额 `bomber:0→1`，见第七节），回到 84.8%；
  `accept.js` 里已加一项"简单 AI 对龟缩流 ≥60%"防回归门禁。
  注意这是**编成**层面的补齐，简单 AI 的战术弱项（`doCharge=0`、`strikeP=.50` 等）全部保留，难度梯度未抹平。
- 地图固定为程序生成（`gen`）与 `scorch`/`f01..f06`；换图用 `--map`。
  采集时若多张图尺寸不同会报错（观测张量需要固定 N），请一次只采一种尺寸。
- 若游戏源码结构大改（`<script>` 不止一块、函数改名、动作原语改名），
  `engine.js` 的导出层与 `collect.js` 的钩子列表需要同步更新；
  `selfcheck` 第 [1] 关与 `selfcheck-collect` 第 [1] 关会立刻报警。
